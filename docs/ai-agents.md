# AI Agents

`AGENTS.md` at the repository root is the canonical instruction file for
agents working **on gin-kit itself**. The gin-kit development skill at
`.github/skills/gin-kit-development/SKILL.md` complements it with concrete
workflows for template changes, generator work, and scaffold validation.

Projects **generated by** gin-kit ship their own agent guidance: an
`AGENTS.md` tailored to the project's edition, mode, database, and ORM, plus
adapters for Claude (`CLAUDE.md`), Gemini (`GEMINI.md`), GitHub Copilot
(`.github/copilot-instructions.md`), and Cursor (`.cursor/rules/gin-kit.mdc`),
and a project-level skill at `.github/skills/gin-kit-development/SKILL.md`.
These files live under `internal/cli/templates/` in this repository and are
rendered at scaffold time.

When an agent changes a template:

1. Read the template source under `internal/cli/templates/` or
   `internal/cli/generators/` and understand how `.gin-kit.yaml` selections
   gate it. Go/code templates use the `.tmpl` suffix; agent guidance files may
   be templated or static.
2. Scaffold framework and starter projects in API and UI modes
   (`.github/scripts/scaffold-smoke.sh` automates this). If the change touches
   the tasks example, also scaffold with `--example` — CI's matrix does not
   cover it.
3. Run `go test ./...` and `go build ./...` in the generated projects.
4. Preserve the canonical response envelope and field-level validation errors.
5. Update English documentation and tests in the same change (see
   "Documentation discipline" in `AGENTS.md`).

## Documentation discipline

Every behavior change must update the documents it affects, in the same pull
request. New features must land with a page or section on the documentation
site (`website/src/content/docs/`), a `CHANGELOG.md` entry under
`[Unreleased]`, and — when the CLI surface changes — an update to
`docs/cli.md`. The full change-type matrix lives in `AGENTS.md`.

## CI and release safety

AI agents may prepare a release checklist, but must not create or push a Git tag without explicit maintainer authorization for the exact version. The release version comes from an annotated `v0.x.y` tag, not from a hand-edited source constant.

Before suggesting a release, an agent must confirm a clean worktree and run the same checks used by CI. Maintainers can follow [docs/releasing.md](releasing.md) to publish and verify the release.
